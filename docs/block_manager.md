# 第一章：用最少的概念理解 BlockManager

[`block_manager.py`](../nanovllm/engine/block_manager.py) 的职责可以压缩成一句话：**给序列分配 KV 缓存块，并让相同前缀复用已经算好的块。**

按照奥卡姆剃刀法则，先只保留三个必要概念：**块、引用计数、前缀哈希**。块解决“存在哪里”，引用计数解决“何时可以回收”，前缀哈希解决“哪些计算可以复用”。其余代码都是这三个概念的具体操作。

## 1.1 为什么需要块

模型生成 token 时，会保存已经计算过的 Key 和 Value，供后续注意力计算使用，这就是 KV cache。序列会不断变长，多个序列又会同时运行，因此需要管理这些缓存占用的空间。

这里把空间切成固定大小的块，每块容纳 `block_size` 个 token 的 KV。一个长度为 `L` 的序列需要：

```text
块数 = ceil(L / block_size)
```

序列通过 `seq.block_table` 记录每个逻辑块对应的物理块编号，物理块不必连续。例如，为方便说明，假设每块容纳 4 个 token：

```text
序列的 token： [a b c d] [e f g h] [i j]
逻辑块编号：       0         1       2
block_table：  [   7,        2,      9   ]
```

第 `p` 个 token（从 0 开始计数）对应的缓存槽位为：

```text
物理块编号 = block_table[p // block_size]
块内偏移   = p % block_size
槽位编号   = 物理块编号 * block_size + 块内偏移
```

这让序列可以按块使用和扩展空间，不必为每个请求预留一整段最大长度的连续缓存。代价是最后一块可能没有填满。

**BlockManager 管理的是编号和元数据。** GPU 上的 KV 张量由 [`ModelRunner.allocate_kv_cache()`](../nanovllm/engine/model_runner.py) 一次性分配，实际写入由 [`Attention`](../nanovllm/layers/attention.py) 完成。这里的“分配块”和“释放块”只是改变使用权，不是申请或释放 GPU 张量。

下文统一用 `B` 表示块大小。示例中的 `B = 4` 仅用于演示；项目默认是 256，实际配置要求为 256 的倍数。引擎启动时会把 `Sequence.block_size` 设置成配置值，保证序列切块和管理器使用同一大小。

## 1.2 用哪些数据记账

`Block` 对应一个物理块，有四个字段：

| 字段 | 含义 |
| --- | --- |
| `block_id` | 固定的物理块编号 |
| `ref_count` | 当前有多少个序列引用这个块 |
| `hash` | 完整前缀的哈希；`-1` 表示尚未登记为可复用的完整块 |
| `token_ids` | 这个块内的 token，用于核对缓存命中；不包含前面块的 token |

`BlockManager` 用四个容器管理这些元数据：

| 容器 | 用途 |
| --- | --- |
| `blocks` | 按编号查找 `Block` |
| `free_block_ids` | 可供分配的块编号队列，引用计数为 0 |
| `used_block_ids` | 正被序列引用的块编号集合，引用计数大于 0 |
| `hash_to_block_id` | 从前缀哈希查找一个可复用的物理块 |

最关键的区别是：**“空闲”表示没有序列引用，不表示里面没有缓存。**

一个完整块在引用计数归零后，可以仍然保留 `hash`、`token_ids` 和 GPU 中的 KV。只要还没被覆盖，后续请求就可以再次使用它。因此，哈希索引既可能指向使用中的块，也可能指向空闲块。

## 1.3 前缀相同，才能复用 KV

仅仅块内 token 相同还不够。比如 `[a b][x y]` 和 `[c d][x y]`，虽然第二块都是 `[x y]`，但它们前面的上下文不同，算出的 KV 也可能不同。

`compute_hash(token_ids, prefix)` 因此把前一个块的哈希和当前块的 token 字节一起交给 `xxhash.xxh64()`：

```text
h0 = H(第 0 块 token)
h1 = H(h0, 第 1 块 token)
h2 = H(h1, 第 2 块 token)
```

首块使用默认 `prefix = -1`，不写入前缀哈希；后续块把前缀哈希编码为 8 字节的小端整数，再加入当前 token 数组的字节。这样每个哈希都把此前上下文串联起来。

查找时还会比较 `block.token_ids == token_ids`。这能排除哈希相同但当前块 token 不同的情况，不过 64 位哈希加当前块比较并不是整个前缀绝无碰撞的数学保证。

缓存只沿着序列开头连续匹配：**遇到第一块未命中，就停止向后查找。** 后面的块依赖前面的上下文，不能仅凭局部 token 相同就跳过去复用。

## 1.4 新序列进入：先算容量，再分配

### `can_allocate()`：同时回答“能复用多少”和“空间够不够”

这个方法的返回值不是布尔值：`-1` 表示空间不足，非负整数表示可复用的前缀块数，`0` 表示可以分配但没有前缀命中。

它只检查 `range(seq.num_blocks - 1)`，也就是**最后一块之前的块**，即使最后一块刚好填满也不参与命中。这保证 prefill（处理输入序列）仍有 token 需要执行前向计算，以得到预测下一个 token 的输出；仅有 KV 缓存并不能直接得到该输出。当前实现按整块复用，因此保留的是整个最后一块的计算。

容量计算可以写成：

```text
需要从空闲池取得的块数
    = 序列总块数 - 命中且已在使用中的块数
```

两种命中的区别在这里非常重要：

- 命中使用中的块：直接增加引用，不消耗空闲块名额。
- 命中空闲块：可以省去计算，但仍要把它从空闲池取出，占用一个名额。

例如，一个序列需要 3 块，前两块命中，其中一块在使用、一块空闲，那么仍需要 2 个空闲块名额：一个取回命中的空闲块，一个用于最后一块。不能因为命中了两块，就认为只需要一个空闲块。

### `allocate()`：把检查结果落实到块表

`allocate(seq, num_cached_blocks)` 要求序列的块表为空，然后分两步处理：

1. 先取得全部命中的前缀块。使用中的块执行 `ref_count += 1`；空闲块则设置 `ref_count = 1`，从空闲队列移到使用集合。两者都保留原有缓存，并把编号加入 `seq.block_table`。
2. 对剩余部分调用 `_allocate_block()`，逐个申请可写入的新块，并追加到块表。

**先取得全部命中块，再申请新块**，可以避免新块分配提前覆盖某个本来准备复用的空闲块。

最后设置：

```python
seq.num_cached_tokens = num_cached_blocks * self.block_size
```

`_allocate_block()` 从空闲队列头取出一个编号。如果旧哈希索引仍指向这个块，就删除该索引；然后调用 `reset()`，把引用计数设为 1、哈希设为 `-1`、token 列表清空，并加入使用集合。旧 GPU 内容此时不必清零，后续前向计算会写入需要的 KV。

删除旧索引时要检查它是否仍指向本块，因为同一个哈希可能已被后续登记的另一个块接管，不能误删新的映射。

这里分配的是序列当前总长度需要的全部块。即使调度器把 prefill 拆成多轮计算，也不会只为本轮 token 分配空间。因此，**拿到块不等于块内 KV 已经算好**。

## 1.5 计算完成：只登记已经填满的块

模型完成本轮前向计算后，调度器调用 `hash_blocks(seq)`。它用两个计数确定哪些块刚刚变完整：

```python
start = seq.num_cached_tokens // self.block_size
end = (seq.num_cached_tokens + seq.num_scheduled_tokens) // self.block_size
```

然后处理逻辑块区间 `[start, end)`：取前一个完整块的哈希作为起点，依次计算哈希，通过 `Block.update()` 保存哈希和 token，并更新 `hash_to_block_id`。如果 `start == end`，说明本轮没有新增完整块，直接返回。

例如 `B = 4`，本轮之前已有 6 个 token 的 KV，本轮再计算 3 个：

```text
计算前： [✓ ✓ ✓ ✓] [✓ ✓ · ·] [·]
计算后： [✓ ✓ ✓ ✓] [✓ ✓ ✓ ✓] [✓]
start = 6 // 4 = 1
end   = 9 // 4 = 2
```

只登记逻辑块 1。块 0 早已登记，块 2 尚未填满。

只共享完整块，使共享的部分在后续生成中保持不变；尚在增长的尾块留给各序列独立写入，所以这条路径不需要写时复制。完整的最后一块也可以在这里登记，供未来更长序列作为前缀复用；“最后一块不参与命中”是分配新序列时的限制。

注意 `num_cached_tokens` 表示**已有有效 KV 的 token 数**：分配时它来自前缀命中，之后也包括本序列自己计算完成的 token，不等于“从其他请求复用的 token 数”。

## 1.6 逐 token 生成：为什么余数为 1 才申请新块

理解 `can_append()` 和 `may_append()`，关键在于调用时机。完成整个 prefill 的那一轮，以及之后每轮 decode 的顺序是：

```text
安排计算 → 模型写入本轮输入的 KV → hash_blocks()
        → 增加 num_cached_tokens → 把采样得到的新 token 加入序列
```

**刚采样出的 token 已经在序列里，但它自己的 KV 要到下一轮前向计算才产生。**

假设 `B = 4`，刚算完前 4 个 token，并采样出了第 5 个。此时 `len(seq) == 5`，而块表仍只有一块。下一轮 decode（逐 token 生成）需要处理第 5 个 token，才必须申请第二块：

```python
len(seq) % self.block_size == 1
```

因此：

- `can_append()`：跨入新块时检查是否至少有一个空闲块；否则不需要额外空间，返回 `True`。源码把上述布尔表达式当作整数 `1` 或 `0` 参与比较。
- `may_append()`：在同一个边界条件下调用 `_allocate_block()`，把新块编号加入块表；它不负责把 token 加入序列。

若空间不足，释放哪个序列由 [`Scheduler`](../nanovllm/engine/scheduler.py) 决定。调度器会抢占序列、调用 `deallocate()`，再将其放回等待队列。

## 1.7 序列退出：归还使用权，保留复用机会

`deallocate(seq)` 在序列结束或被抢占时执行：

1. 逆序遍历块表，对每个块执行 `ref_count -= 1`。
2. 只有计数降到 0，才调用 `_deallocate_block()`，从使用集合移除编号，并追加到空闲队列尾部。
3. 将序列的 `num_cached_tokens` 清零，并清空块表。

如果两个序列共享一个块，一个退出后计数只是从 2 变成 1，另一个仍能正常使用它。计数变成 0 后，块中的缓存仍保留，直到重新分配覆盖。

空闲队列从头分配、从尾归还。同一序列逆序归还时，尾部块先入队、前缀块后入队，因此该序列前缀块会排在更后面，较晚被重新分配覆盖。这是队列顺序带来的效果，代码没有维护按访问时间排序的 LRU 缓存。

## 1.8 用一个例子串起全部过程

仍设 `B = 4`，请求 A 为 `[a b c d][e f]`，初始没有缓存。下面省略后续生成，只观察前缀共享和释放：

| 时刻 | 块和缓存发生的变化 |
| --- | --- |
| A 分配 | 没有前缀命中，取得物理块 0、1，块表为 `[0, 1]` |
| A 的输入计算完成 | 6 个 token 的 KV 已写入；块 0 填满并登记哈希，块 1 尚未登记 |
| 请求 B 到来：`[a b c d][x y]` | 第一块命中块 0，引用计数从 1 变成 2；尾块另行分配，例如得到块 2 |
| B 执行 prefill | `num_cached_tokens = 4`，只计算 `[x y]`，注意力读取共享块 0 中的前缀 KV |
| A 释放 | 块 1 归还空闲池；块 0 的引用计数从 2 变成 1，仍由 B 使用 |
| B 释放 | 块 2 和块 0 归还空闲池；块 0 的前缀缓存仍可命中 |
| 后续再次需要 `[a b c d]` 前缀 | 若块 0 尚未被重新分配，就可以从空闲池取回复用；若已被覆盖，则重新计算 |

对应到源码，阅读顺序就是：`can_allocate()` 判断资源与命中 → `allocate()` 建立块表 → `hash_blocks()` 登记计算结果 → `can_append()` / `may_append()` 支持增长 → `deallocate()` 归还引用。始终区分三件事：**块有没有被引用、块内 KV 有没有算好、完整块有没有登记为可复用前缀**。
